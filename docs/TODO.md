# TODO

## 背景

重构期间，MovScript 需要明确内容单元提示词在引用上游实体时如何处理候选和选择关系。

这里讨论的是 `edit_prompt` 中的语义引用，例如：

```text
使用 {{asset::hero_base}} 作为角色一致性参考。
使用 {{storyboard::opening_panel}} 作为构图参考。
```

这类引用最终会解析到上游 `content_unit` 的候选输出，并在提示词编译时转换为后端资源引用，例如 `@[resource:123]`。

本文记录未来目标行为，当前实现可能仍要求上游必须存在明确 `selection`。

## 适用范围

本文适用于通过实体引用间接找到上游内容单元的提示词引用：

- `{{asset::id}}`
- `{{storyboard::id}}`
- `{{keyframe::id}}`
- `{{scene_moment::id}}`
- `{{expression_unit::id}}`
- `{{content_unit::id}}`

直接引用不在本文的自动选择规则内：

- `{{resource::123}}` 直接解析到资源。
- `{{candidate::id}}` 已经显式指定候选，不需要根据候选数量推断。

## 目标规则

| 上游候选数量 | 上游选择状态 | 提示词编译结果 | 说明 |
| --- | --- | --- | --- |
| 0 | 无选择 | 无法编译 | 没有任何可引用输出，返回 blocker。 |
| 1 | 无选择 | 使用唯一候选编译 | 唯一候选可作为当前候选参与本次提示词编译。 |
| 多个 | 无选择 | 无法编译 | 存在歧义，必须先由用户或工作流选择一个候选。 |
| 任意数量 | 有选择 | 使用已选择候选编译 | 选择仍是稳定依赖的最高优先级。 |

核心意图：

1. 没有候选时，引用 `asset` 等实体的提示词无法编译。
2. 只有一个候选且没有选择时，引用提示词使用当前唯一候选编译。
3. 有多个候选且没有选择时，引用提示词无法编译。

## 单候选回退的边界

单候选回退只影响提示词编译，不应自动写入 `selection`。

也就是说，编译器可以临时把唯一候选投影成资源引用，但这不等价于用户采纳了该候选。稳定依赖、候选审阅、stale impact 和 regeneration decision 仍应以正式 `selection` 为准。

如果唯一候选没有可解析的 `resource_id` 或输出资源，提示词仍然无法编译，并返回资源缺失 blocker。

## 多候选阻塞的原因

当存在多个候选且没有选择时，系统无法判断用户希望使用哪一个视觉、音频或视频结果。此时继续编译会把下游生成绑定到一个未经确认的输出，容易造成后续 stale 判断和审阅链路混乱。

因此多候选无选择应明确阻塞，并引导到候选选择或审阅界面。

## 实现备注

后续实现时，提示词编译入口应从 Project Service 或等价项目视图读取统一的 candidate/selection 上下文，而不是分别拼接 source 和 backend decision。

建议解析顺序：

1. 先根据实体引用找到上游 `content_unit`。
2. 读取该内容单元的 backend decision context。
3. 如果存在有效 `selection`，使用选择指向的候选或资源。
4. 如果没有 `selection` 且候选数量为 1，使用唯一候选的首个可用资源。
5. 如果候选数量为 0，返回无候选 blocker。
6. 如果候选数量大于 1，返回选择缺失或歧义 blocker。

阻塞结果应区分原因，便于 UI 和 Agent Surface 给出正确下一步：

- 没有候选：需要先生成或导入候选。
- 多个候选无选择：需要先选择候选。
- 候选无资源：需要检查候选生成结果或资源登记。
