# MovScript Admin v2 视觉定义

本文档定义 Admin v2 的视觉方向和信息呈现规则。目标不是“更漂亮”，而是让用户在管理 AI 视频能力时：

```text
容易配置
状态清晰
知道下一步
复杂能力可以逐层展开
```

Admin v2 只有一套视觉系统。Local 和 Cloud 的区别是内容多少，不是视觉语言不同。

## 1. 产品视觉定位

Admin v2 应该像一个 **Production Setup Console**：

- 它不是营销页
- 不是传统数据库后台
- 不是堆满指标的 SaaS 仪表盘
- 也不是只给工程师看的 debug panel

它的核心气质应该是：

```text
安静
明确
可执行
有证据
不吓人
能逐层深入
```

一句话：

> Admin v2 是一个让用户把 AI 视频生产能力接起来、看清楚、修得动的控制台。

## 2. 视觉要解决的问题

### 2.1 配置容易

用户进来时不应该先看到一堆后台对象，而应该看到一个明确任务：

```text
你现在缺什么？
下一步点哪里？
点完会发生什么？
会不会花钱或影响已有配置？
```

因此视觉上要优先呈现：

- 当前状态
- 推荐动作
- 验证结果
- 影响范围
- 可回退或可查看详情的入口

### 2.2 状态清晰

AI 生成系统复杂，但用户不应该自己判断错误位置。

视觉上必须把状态拆成链路：

```text
Key
能力模板
模型/线路
素材中转
Worker
生成测试
```

每个节点只有少数状态：

```text
可用
缺失
警告
阻塞
检查中
未启用
```

不要让用户从 raw error、route id、provider response 里猜状态。

### 2.3 复杂度可展开

Local 用户默认看 Primary。

Cloud 用户默认看 Primary + Detail。

高级用户可以展开 Advanced。

视觉层级固定为：

```text
Primary：我现在该做什么
Detail：为什么是这个状态
Advanced：内部对象和精细控制
```

不要把 Advanced 混进 Primary。

## 3. 页面内容模型

每个页面都必须回答四个问题：

| 问题 | 页面区域 | 示例 |
| --- | --- | --- |
| 当前是什么状态？ | 状态区 | 文生视频可用，图生视频缺素材中转 |
| 为什么是这个状态？ | 证据区 | Key 可用、线路可用、Public URL 缺失 |
| 下一步做什么？ | 动作区 | 配置素材中转 |
| 会影响什么？ | 影响范围 | 图生视频、视频参考、素材库 |

如果一个模块不能回答这四个问题之一，就不应该出现在主视图。

## 4. 统一页面骨架

Admin v2 只允许三种主页面骨架。

### 4.1 Status + Next Action

用于：

- 开始
- Cloud 启动中心

结构：

```text
左：主状态
中：链路 / 覆盖率
右：下一步动作
下：最近结果 / 风险
```

适合回答：

> 现在系统离可用还差什么？

### 4.2 Form + Verification

用于：

- 接入 Key
- 素材中转
- Cloud Provider 接入
- Cloud 资源与存储

结构：

```text
左：表单
中：预览 / 能力映射
右：验证步骤
底：确认动作
```

适合回答：

> 我填什么？系统会改什么？验证是否通过？

### 4.3 List + Inspector

用于：

- 视频能力
- 失败诊断
- 模型与路由
- 任务与调用
- 高级

结构：

```text
左：列表 / 表格
右：详情 Inspector
底 / 折叠：高级详情
```

适合回答：

> 哪一项有问题？点开后为什么？怎么修？

## 5. 视觉层级

### 5.1 页面标题

页面标题必须是用户任务，不是内部对象名。

推荐：

```text
接入 Key
视频能力
素材中转
失败诊断
```

避免：

```text
Provider Registry
Catalog Entries
Route Binding Matrix
Runtime Debug Logs
```

Cloud 可以在标题中加入对象，但仍要有任务语义：

```text
接入 / Provider
模型与路由
任务与调用
权限与审计
```

### 5.2 主状态区

主状态区必须用短句，不用指标堆叠。

好：

```text
文生视频已可用
图生视频还缺素材中转
当前 Key 验证失败
```

不好：

```text
Provider configured: 1
Route bindings: 4
Catalog entries: 7
```

指标可以在 Detail 或 Cloud 中出现，但不能替代状态解释。

### 5.3 下一步动作

每页只允许一个 Primary action。

Primary action 必须符合当前状态：

| 状态 | Primary action |
| --- | --- |
| 缺 Key | 接入 Key |
| Key 无效 | 重新验证 |
| 文生视频可用 | 测试生成 |
| 图生视频缺中转 | 配置素材中转 |
| 失败未知 | 打开专注诊断 |

不要同时出现多个同权重按钮。

### 5.4 证据区

证据区用 checklist，不用大段文字。

示例：

```text
Key 可用
能力模板已应用
文生视频线路可用
素材中转缺失
Worker 就绪
```

证据必须能点击跳转到来源页面或详情。

### 5.5 高级详情

高级详情必须折叠或放在 Inspector 底部。

包括：

- provider model id
- public model id
- route group
- priority
- weight
- concurrency
- raw request
- raw response
- JSON

这些内容不能出现在主状态区。

## 6. 组件视觉规则

### 6.1 Shell

Admin Shell 要稳定，不要抢内容：

- 左侧导航宽度固定
- 顶部状态条高度固定
- 内容区域使用统一 gutter
- 页面标题区和主内容之间留出明确分隔

Local 和 Cloud 使用同一 Shell。

### 6.2 导航

导航不是功能大全，而是任务地图。

视觉规则：

- 当前页高亮清晰
- 状态点只在必要时显示
- Cloud 分组只用轻量标题
- 不使用大图标或彩色卡片式导航

### 6.3 状态点

状态点统一语义：

| 状态 | 颜色 | 用法 |
| --- | --- | --- |
| ready | 绿色 | 已可用 |
| missing | 灰色 | 还没配置 |
| warning | 琥珀 | 可部分使用，有建议 |
| blocked | 红色 | 当前阻塞 |
| checking | 蓝色 | 正在检查 |
| disabled | 灰色低对比 | 未启用 |

颜色只用于状态，不用于装饰。

### 6.4 卡片和面板

卡片只能用于模块边界，不用来制造装饰。

规则：

- 不做卡片套卡片
- 不做大圆角卡片堆叠
- 不做营销式 bento
- 表格和列表优先于卡片瀑布

### 6.5 表格

表格是 Cloud 和高级页的主力组件。

Local 表格要少列：

```text
能力 / 状态 / 当前接入 / 最近检查 / 操作
```

Cloud 表格增加列，但保持同一行高、字体、操作区：

```text
能力 / 状态 / Provider / Route / Team / Cost / Quota / 最近检查 / 操作
```

### 6.6 表单

表单要和验证结果放在同一个屏幕里。

不要让用户填完表单后跳到另一个页面才知道是否成功。

布局：

```text
表单字段
能力预览
验证步骤
影响范围
确认动作
```

密钥字段必须有安全提示：

```text
密钥由用户输入，Agent 不读取明文。
```

### 6.7 Inspector

Inspector 是 Admin v2 的关键组件。

统一结构：

```text
标题
当前状态
阻塞原因
证据
推荐动作
影响范围
高级详情
```

用户点击任何列表行，都应该在 Inspector 中看到“为什么”和“下一步”。

## 7. 信息密度

Admin v2 应该是中等密度，不是空，也不是压迫。

### 7.1 Local 密度

Local 只展示：

- 当前状态
- 一个主动作
- 关键链路
- 少量最近结果
- 必要的验证信息

### 7.2 Cloud 密度

Cloud 可以展示：

- 多 provider
- route coverage
- worker pool
- storage/CDN
- quota
- cost
- audit risk

但仍然遵守同一层级：

```text
先状态
再证据
再操作
最后高级
```

Cloud 可以更多，但不能更乱。

## 8. 色彩与字体

### 8.1 色彩

推荐色彩方向：

```text
背景：#F7F8FA / #FFFFFF
主文字：#111827
次文字：#667085
边框：#E5E7EB
主强调：#0F766E 或 #0E7490
成功：#16A34A
警告：#D97706
错误：#DC2626
信息：#2563EB
```

避免：

- 大面积紫蓝渐变
- 过暗后台风
- 暖黄/米色为主
- 过多彩色状态同时出现

### 8.2 字体

字体气质应该是工具型、清晰、低装饰。

建议：

- 中文：系统默认 sans 或项目现有字体
- 标题：16-24px
- 页面主标题：24px 左右
- 表格正文：13-14px
- 状态标签：12px
- 不使用负字距
- 不随 viewport 缩放字号

## 9. 图标

图标只服务识别，不做装饰。

必须出现的图标类型：

- 导航图标
- 状态图标
- 动作图标
- 验证步骤图标
- 折叠 / 展开图标

图标风格：

- 线性
- 统一 stroke
- 小尺寸
- 不使用彩色插画图标

## 10. 动效

动效只用于帮助理解状态变化。

可以有：

- 检查中 spinner
- 验证步骤逐项完成
- Inspector 切换
- 状态从 missing 到 ready 的轻微过渡

不要有：

- 装饰性背景动效
- 大面积渐变流动
- 卡片漂浮
- 营销页式进入动画

## 11. 配置流程视觉原则

配置流程必须一直让用户看到四件事：

```text
我正在填什么
系统会自动做什么
验证通过了什么
还缺什么
```

以“接入 Key”为例：

```text
左：Base URL / API Key
中：将启用哪些能力
右：验证步骤
底：测试并应用
```

如果失败：

```text
失败原因
证据
可修动作
高级详情
```

不要只显示 toast。

## 12. 清晰度验收标准

一个 Admin v2 页面设计必须通过这些问题：

1. 用户 3 秒内能不能知道当前状态？
2. 用户能不能知道下一步点哪里？
3. 用户能不能知道这个动作会影响什么？
4. 用户能不能不用理解 route/catalog/provider id 就完成基础配置？
5. 高级用户能不能找到内部对象，但不干扰初级用户？
6. Local 和 Cloud 是否看起来是同一个产品？
7. Cloud 是否只是更多内容，而不是另一套界面？
8. 出错时是否有证据和修复动作，而不只是错误码？

## 13. 后续视觉稿顺序

下一轮视觉稿不再单独画散页，而是先画三张核心系统图：

1. **视觉系统板**
   - Shell
   - 状态条
   - 三种页面骨架
   - 状态色
   - 按钮 / 表格 / Inspector / 验证面板

2. **配置主流程图**
   - 接入 Key
   - 能力预览
   - 验证步骤
   - 成功 / 部分成功 / 失败状态

3. **Local / Cloud 同页对照图**
   - 同一个页面骨架
   - Local 少内容
   - Cloud 多内容

先定视觉系统，再继续画完整页面。
