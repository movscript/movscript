# Movscript 上线前历史包袱清理原则

本文档记录 Movscript 正式上线前的清理理念。它不是发布兼容承诺，而是一次把开发期探索成本归零的工程准则。

## 核心判断

Movscript 还没有正式对外稳定发布时，开发期形成的迁移历史、兼容入口、契约 fixture、边界守门测试，不应自动成为正式版必须背负的长期兼容债。

上线前应以当前产品形态为基线：

- 当前代码能构建。
- 当前核心流程能跑通。
- 当前数据库能从空库初始化。
- 当前前后端、Electron、provider 和 workspace 的实际运行边界清楚。

满足这些条件后，开发期历史不需要继续兼容。

## 基本原则

### 1. 当前有效优先于历史兼容

只保留当前运行时、当前产品路径、当前发布包真正需要的结构。

如果一个契约、迁移、alias、fixture 或测试只是在证明过去某次重构没有倒退，而现在已经不再服务真实运行路径，可以删除。

### 2. 未正式发布前不承诺历史数据升级

正式上线前，数据库可以压成一个初始 baseline。

默认策略：

- 支持正式版空库初始化。
- 不承诺迁移开发期、测试期、预研期旧库。
- 删除旧 checksum 兼容、legacy no-op 迁移、旧字段回填、旧表搬迁逻辑。

如果确实有必须保留的内测数据，应单独写一次性导入脚本，而不是把所有历史迁移永久留在产品代码里。

### 3. 契约不是越多越安全

契约只有在约束真实边界时才有价值。

应保留的契约：

- 当前 Electron preload 与 renderer 的 IPC 类型边界。
- 当前前后端 API 或 app-server wire shape。
- 当前导入、导出、快照、调试包仍会读写的格式。
- 当前 provider/runtime 必须共享的能力声明。

应清理的契约：

- 只服务开发期重构的 fixture。
- 已无消费者的 JSON schema。
- 标记 deprecated 且没有正式用户数据依赖的字段。
- 为防止旧目录、旧命名、旧 alias 回流而写的一次性守门测试。
- 只描述未来可能变化形态的“预留契约”。

### 4. 测当前行为，不测历史影子

清理后测试重点应转向当前行为：

- 空库启动和迁移初始化。
- 核心用户路径。
- 当前 API shape。
- 发布打包和资源校验。
- 当前 workspace、agent、media、provider 的真实业务流程。

不要继续为已经删除的历史路径维护测试。测试应该证明产品现在能工作，而不是证明过去的重构还没有被撤销。

### 5. 删除兼容层时同步删除命名

当一个旧概念被清理时，应同时删除：

- 代码路径。
- 类型 alias。
- 配置环境变量兼容名。
- README 中的旧命名。
- fixture 和 schema。
- 对应的 contract/boundary test。

不要只删实现，留下旧名字继续污染判断。

## 清理决策表

| 对象 | 默认处理 | 保留条件 |
| --- | --- | --- |
| 开发期数据库迁移 | 压缩为正式版 baseline | 已有必须升级的真实用户/内测数据 |
| legacy no-op migration | 删除 | 无 |
| 旧 checksum 兼容 | 删除 | 仍允许旧库直接升级 |
| 旧字段回填 | 删除 | 仍允许旧 schema 数据升级 |
| JSON schema 契约 | 按消费者保留 | 当前运行时、导入导出、调试归档仍读取 |
| fixture | 删除 | 当前测试仍用来验证真实业务格式 |
| deprecated 字段 | 删除或升新版本 | 已发布格式需要继续读取 |
| boundary/contract test | 精简 | 仍约束当前架构边界 |
| compatibility alias | 删除 | 外部已发布入口仍依赖 |
| 文档中的早期/兼容说明 | 改写 | 仍准确描述正式版行为 |

## 数据库清理方向

推荐把正式版数据库定义为 `v1 baseline`：

1. 保留迁移框架和 `schema_migrations` 表。
2. 用一个初始迁移创建当前完整 schema。
3. 删除开发期逐步演进的历史迁移。
4. 删除 legacy checksum 接受逻辑。
5. 删除只为旧表、旧字段、旧模型 ID 服务的回填函数。
6. 正式版之后的新 schema 变化再从新的递增迁移开始。

这样上线后的迁移历史是干净的：正式版之前的探索不进入正式版之后的长期维护成本。

## 契约清理方向

推荐把契约分成三类：

### A. 当前运行契约

继续保留，并让测试覆盖它。

例子：当前 IPC 类型、当前 provider 能力 shape、当前导入导出 snapshot。

### B. 开发期守门契约

默认删除或合并成更小的架构说明。

例子：防止旧目录回流、旧 script 名回流、旧 alias 回流的测试。

### C. 未来预留契约

默认删除。

如果未来会变，就不要现在把它当稳定契约维护。等真实功能落地时，再按当时的实现写契约。

## 工作方式

每次清理前先问三个问题：

1. 当前正式版运行时还会读它吗？
2. 当前正式版用户路径还依赖它吗？
3. 删除它后，只跑当前构建、当前测试、当前核心流程，是否仍然成立？

如果答案是“不读、不依赖、当前能过”，就可以删。

如果答案不确定，不要因为“可能未来有用”而保留。未来需要时重新设计，比现在背一个不准确的旧契约更便宜。

## 上线前目标

上线前清理的目标不是让仓库看起来历史完整，而是让正式版起点足够清楚：

- 数据库从一个干净 baseline 开始。
- 契约只描述当前真实边界。
- 测试只保护当前产品行为。
- 文档只讲正式版事实。
- 旧名字、旧入口、旧 schema 不再影响后续判断。

这次清理完成后，正式版之后再新增的迁移、契约和兼容承诺，才进入长期维护范围。
